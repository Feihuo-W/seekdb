# MiniVectorDB 性能优化日志

## 测量方法

- 工具：`minivectordb/tools/bench.py`（仓库内，可复现）。
- 负载：官方 benchmark 形状——10,000 行 × 128 维向量，每批 100 行写入并提交；
  随后 1,000 次 TopK 查询，K=10，其中一半带 `category` 等值过滤。
- 指标口径：
  - `T_write`：全部批次请求 + 结果输出 + 持久化的墙钟时间。
  - `T_query`：全部查询请求处理与结果输出的墙钟时间（不含装载/预热）。
  - `B`：`/proc/<pid>/io` 的 `read_bytes + write_bytes` 增量（块设备 I/O 近似；
    平台正式口径为 cgroup v2 `io.stat`，含页缓存写回）。
  - `M`：`/proc/<pid>/status` 的 `VmHWM`（峰值 RSS；平台正式口径为 cgroup
    `memory.peak`，含文件页缓存，数值会更大）。
  - `Recall@10`：抽样查询（含有过滤/无过滤）与 Python 暴力真值比较；
    每轮另校验返回行数=K、无重复、满足过滤、重启后数据仍在。
- 环境：WSL2 Linux x86_64，16 核，g++ 9.4 `-O3`，CPU 支持 AVX2/FMA。
- **噪声与对比方法**：本机 `fdatasync` 抖动大（写入 1.8–3.6s），宿主负载随时间漂移，
  跨时段跑分不可比。因此效果结论采用**逐轮交替的配对 A/B**：同一会话内
  `v0 → 优化版 → v0 → 优化版 …` 交替各跑 6 轮单轮基准，取各自中位数比较。
  微基准（同会话连续测多种查询）用于定位瓶颈。早先「先跑完基线 5 轮、再跑优化 5 轮」
  的顺序对比会把机器预热/漂移计入优化收益（曾得到 −35.2%），仅作参考。

## 瓶颈定位（微基准，单会话）

| 查询类型 | v0/v1 | v2 | v3 | v5 |
| --- | --- | --- | --- | --- |
| 未过滤 TopK（ORDER BY distance LIMIT 10） | 0.984ms | 0.692ms | 0.721ms | 0.583ms |
| 过滤扫描（WHERE category，无距离） | 0.588ms | 0.340ms | 0.281ms | 0.255ms |
| 过滤后 TopK | 0.491ms | 0.390ms | 0.402ms | 0.211ms / v6 0.170ms |

未过滤 TopK 需顺序读取全部 ~5MB 向量，属**内存带宽受限**：
- v1 降低计算占比（少一次 sqrt、SIMD 多累加器），带宽受限处单独看不出收益；
- v2 扁平扫描把红黑树逐节点跳转改为顺序遍历，显著提升带宽利用；
- v3 省去热路径每行 `ColAt`，收益在噪声内（中性）；
- v5 解决过滤查询的「页粒度放大」：行式布局下读 `category` 会连带把该页上的向量
  拉入缓存，过滤命中率仅 1% 也要扫完整份数据；改为按 scan 顺序缓存过滤列值后，
  过滤阶段只读紧凑标量数组，仅对命中行读向量，过滤 TopK 近乎减半。

## 各版本改动明细

### v1（`12ceef850`）计算路径
- 行内布局改为「定长列（BIGINT/VECTOR）在前 + VARCHAR 长度表 + VARCHAR 字节」，
  向量列偏移与字符串长度解耦，扫描无需逐列行走（`Schema::ComputeLayout`）。
- 距离比较改用**平方距离**（单调等价），扫描期不再每行 `sqrt`。
- AVX2/FMA 由单累加器改为 **4 累加器**，打破 FMA 依赖链。
- 行格式变更，旧 `/data` 不兼容（提测每次从空目录开始，无影响）。

### v2（`1d4cae9c5`）扫描结构
- `TableState` 增加扁平 `scan`（pk 有序的 `(pk, RowRef)` 数组）+ `scan_dirty`；
  无事务 overlay 时顺序扫描，提交/压缩后置脏、惰性重建。
- 事务内仍走 map+overlay 归并，保证读己之写正确。

### v3（`347894135`）热路径取址
- TopK 循环预先取出 `vec_off`、查询向量指针与维度，每行直接 `v.p + vec_off`
  取向量，省去 `ColAt` 调用与边界检查。

### v4（尝试后回退）
- 为无过滤 TopK 写了一个绕过 `ForEachRow` 的紧凑扫描循环，微基准未见收益
  （0.69ms 量级不变），确认已达带宽/协议上限；为避免重复代码与风险已回退。

### v7（尝试后回退）多线程扫描
- 评测容器为 2 核，尝试把无过滤 TopK 的扫描按 pk 区间切成两段、各用独立局部堆，
  再归并并做 double 复核。
- 微基准（同会话重复 3 次）未过滤 TopK 0.70–0.91ms，反而劣于单线程 v6 的 0.54ms：
  该负载是内存带宽受限，两线程共享同一带宽没有收益，还要付出每查询创建线程
  （约数十微秒）与缓存争用的代价。已回退，避免无谓复杂度。

### v6 过滤列整数化
- 过滤列缓存由「每行存字符串」改为「intern 为 uint32 id + 字典」：缓存构建时把
  列值映射为 id（内存 4B/行），查询时先查字典拿到目标 id，再在整数数组上过滤；
  目标值不在字典中时直接返回空结果，连扫描都省掉。
- 目的是消除每行字符串比较（约 10k 次/查询）。微基准过滤 TopK 0.211→0.170ms；
  整负载受未过滤查询与协议开销支配，配对 A/B 无法分辨（噪声内）。
- 缓存仍随 `scan` 重建失效，事务内回退通用路径，正确性由差分测试与场景脚本覆盖。

### v5（`d50087ffd`）过滤列缓存
- `TableState` 增加与 `scan` 对齐的 `cache_str/cache_int` 与 `cache_col`；
  当查询是对单列的等值过滤、无事务 overlay、表 ≤50 万行、VARCHAR ≤64 字符或
  BIGINT 时，首次按 scan 顺序抽取该列值缓存，后续查询只在内存数组上比较；
  仅命中行再读取整行向量。
- 缓存随 `scan` 重建而失效（插入/更新/删除/压缩都会置 `scan_dirty`），
  事务内自动回退到通用路径，正确性不受影响；大表或长字符串不启用（保持内存有界）。

## v8 快速浮点解析（`ecfd4e999`）

- 大语句的主要开销是浮点字面量解析：2 万行 × 128 维 = 256 万个数字。
- 实现 `fastfloat.h`：≤15 位有效数字且十进制指数在 [-22,22] 时，尾数与 10^k 均可被
  double 精确表示，单次 IEEE 除法/乘法即得到与 strtod 一致的正确舍入结果；
  其余情况回落 `strtod`。
- 效果：单条 2 万行 INSERT 的响应时间 1.44s→0.88s（−39%），批量写入 0.78s→0.57s；
  公开用例与 229 项自测结果完全一致（浮点语义不变）。

## v9 超内存数据与回包加固（准入修复）

平台反馈单一用例「JSON response timeout」。对照题面与公开题包 README 定位到两类
根因并修复：

1. **协议**：README 明确「每个非空行是一条完整 SQL 或驱动指令」「驱动指令不占断言
   位置」。此前实现有跨行缓冲（Balance 判定未闭合就等待续行）与指令空闲 ack：
   - 跨行缓冲在驱动匀速 pipelining 时可能永不触发空闲 flush，整条语句得不到响应；
   - 空闲 ack 会向不期待指令响应的驱动注入多余 JSON，造成后续断言错位。
   现改为**按行立即处理**：每行 SQL 立刻回一条 JSON；`;`、纯注释等无语句行也回
   `syntax_error`；指令一律不回包；删除跨行缓冲与 ack。hostile_driver 新增
   「看似未闭合行的匀速 pipelining 必须逐行按序回包」回归项。
2. **超内存数据**（题面 2.3：正式测试包含数据量超过内存限额的场景）：行体虽已在
   mmap 文件中，但执行器仍会整表物化——SELECT 把全部行建成 OutVal 数组再拼整表
   JSON，UPDATE 先把所有命中行体收集到内存。大数据用例在此 OOM 被杀，驱动侧表现
   为等不到 JSON 响应。改为：
   - SELECT 结果**逐行流式输出**（64KB 缓冲直写 stdout），不再拼整表字符串；
   - 排序仅保存 {主键, 距离, 行视图} 轻量引用（40B/行），`ORDER BY ... LIMIT` 用
     有界堆，无 LIMIT 全排序也只存引用；比较器直接读 mmap 列值，无每行分配；
   - 自动提交 UPDATE/DELETE 把新行版本/墓碑**流式写入 WAL 事务**，内存只留主键
     列表；行视图在每次追加前完成解码（WAL 增长可能 mremap）；
   - 压缩不再复制整表主键索引（改为扁平偏移表），WAL 阈值 128→256MiB，减少大表
     全量重写次数；**正常关闭不再压缩**（驱动等待进程退出，重写 GB 级快照会拖慢
     退出），重启由有界 WAL 重放恢复。

验证（本机 16 核/7.6GiB，无 cgroup 限额，用 RssAnon 区分匿名内存与可回收页缓存）：

| 项 | 结果 |
| --- | --- |
| 3M 行 × 128 维（约 1.66GiB 行数据）装载 | 204.9s，14.6k 行/s |
| 全表无序 SELECT（3M 行流式输出） | 10.2s，正确 |
| 全表 ORDER BY（无 LIMIT，引用排序） | 15.7s，顺序与并列规则正确 |
| 过滤 TopK / ORDER BY+LIMIT | 0.7s / 0.3s |
| 批量 UPDATE 1M 行、DELETE 300k 行（流式 WAL） | 16.7s / 0.2s，affected_rows 正确 |
| --restart + 恢复 | 5.8s，更新/删除/TopK 全部一致 |
| 最终内存 | **RssAnon 245MiB**，RssFile 1624MiB（可回收页缓存） |
| 官方形状 benchmark（10k 行/1000 查询，3 轮中位） | T_query 503.9ms（v5 为 500.4ms，持平），Recall@10=1.0，I/O 5,971,968B 不变 |

回归：公开 20/20、spec 229/229、hostile 0 失败、fuzz 6 种子、crash 4 种子、
scenario（含 50 万行）、stress_recovery 全量（压缩窗口/恢复期连杀/提交后强杀）
均 0 失败。

## v10 增量压缩（准入修复·第二轮）

v9 之后平台仍报同一用例「JSON response timeout」。本轮不再猜测协议，而是给
`bigdata_check.py` 加了**逐响应延迟统计**，直接测量装载期间每条语句的响应时间：

- 1M 行 × 128 维装载中，绝大多数 500 行 INSERT 批响应约 30ms，但**触发压缩的那一批
  耗时 3.276s**——`Compact()` 在提交响应路径上同步重写整表快照（当时约 530MB）并
  `fsync`。3M 行规模下旧路径要重写 1.58GiB，本机即需 5–15s；平台 2 核配额、内存
  限额与更慢磁盘下会进一步放大，足以超过驱动的单响应超时。这是唯一能让一条小语句
  阻塞数秒的路径，且恰好由题面 2.3 要求的超内存用例触发。
- 同时审计排除了解析器死循环（`Fail` 为 `[[noreturn]]` 抛异常，所有循环均前进）。

修复：把压缩改为**增量会话**，任何单条响应承担的压缩工作有上界：

1. WAL 超过 256MiB 后，在下一条语句开始时于事务边界记录水位并启动会话；
2. 每条语句最多做约 50ms / 64MB 的快照重写（`snapshot.tmp`），同时把水位之后的
   WAL 增量复制到 `wal.tmp` 并随手 `fdatasync`；
3. 每次刷 4MB 快照缓冲后用 `sync_file_range` 触发异步写回，避免收尾 `fsync`
   一次性 flush 整表（实测收尾 sync 仅 18–46ms）；
4. 收尾用一次有序归并更新行引用（快照重定位 + WAL 引用按水位平移），再依次原子
   `rename` 快照与 WAL。实测收尾：sync 18–46ms、swap 25–750ms、relocate 120–548ms；
5. 恢复不变式：PUT/DEL 是按主键的绝对操作，因此「新快照 + 水位之后全部事务重放」
   精确收敛。崩溃落在任一窗口（旧快照+完整 WAL／新快照+完整 WAL／新快照+WAL 尾部）
   均可恢复；启动与正常关闭都直接丢弃未完成会话。

| 项 | v9（同步压缩） | v10（增量压缩） |
| --- | --- | --- |
| 1M 行装载最慢单响应 | **3.276s** | **0.290s** |
| 3M 行装载最慢单响应 | 数秒～数十秒（整表重写） | **1.177s** |
| 1M 行装载吞吐 | 27.3k 行/s | 21.2k 行/s（延迟有界的代价） |
| 3M 行/1.66GiB 全量验证 | 通过 | 通过：装载 170.2s、全表扫描 11.8s、全排序 13.5s、过滤 TopK 0.4s、批量 UPDATE 1M 行 5.1s、DELETE 300k 0.3s、重启恢复 7.7s、RssAnon 245MiB |
| 官方形状 benchmark（3 轮中位） | T_query 503.9ms | T_query 393.0ms、T_write 1607.5ms、I/O 5,971,968B 不变、Recall@10=1.0 |

回归：公开 20/20、spec 229/229、hostile 0 失败、fuzz 6 种子、crash 4 种子、
scenario（含 50 万行）0 失败；`stress_recovery.py` 新增**增量压缩会话内强杀**
（会话期间交错显式事务 COMMIT/ROLLBACK，强杀后再在恢复途中强杀，校验提交保留、
回滚不现、行数与内容一致）。

## v11 官方 JSONL 协议对齐（准入修复·第三轮）

检查官方远程分支发现新提交 `f4d4e2665`（11-10 11:30「upload stdin/stdout protocol
and one demo py to double check」）：题包新增根目录 `STDIO_PROTOCOL.md` 与
`protocol_check/` 官方自测驱动，**正式判题协议首次完整公布**。逐条核对发现 v10
实现与官方协议存在根本差异：

| 项 | v10 实现 | 官方要求 |
| --- | --- | --- |
| 就绪握手 | 仅 stderr 日志 | stdout 第一行恰好 `{"type":"ready"}`，恢复完成后、读请求前主动输出并 flush |
| 请求格式 | 裸 SQL 行 | JSONL：`{"id":1,"op":"execute","sql":"...","search_mode":"exact"}` |
| 响应格式 | `{"columns":...}`/`{"error":"code"}` | 回传同类型 `id` + 布尔 `ok`；错误为 `{"code","message"}` 对象 |
| 关闭 | `--restart` 指令/EOF | `{"op":"shutdown"}` 请求 → `ok:true` 响应 → 退出码 0，stdout 静默 |

规范第 2 节明确：「程序启动后直接等待 SQL、只向 stderr 输出 ready……判题器可能报
JSON response timeout」——与平台三次反馈的报错完全吻合。合并官方分支后改造：

1. `main.cpp` 新增请求解析器（容忍空白、`\uXXXX` 含代理对、id 按原始 JSON 令牌
   回传保持类型），stdout 握手，execute/shutdown 分发；响应信封把 `id` 拼接进
   引擎 payload（流式输出同样适用），每请求按 `search_mode` 切换模式；
2. `json.h`/引擎流式头改为 `ok:true`/`ok:false+error{code,message}` 官方载荷；
3. SQL 解析器 `ExpectEnd` 接受一个尾随分号（JSONL 的 sql 字段自带分号）；
4. 保留非 `{` 开头行的裸 SQL 回退路径，本地工具链不受影响。

**官方工具实测抓到一个真实 bug**：首轮 `protocol_check --handshake-only` 报
`shutdown failed`——官方驱动用 `json.dumps` 默认格式（冒号后带空格），而解析器
在冒号后未跳空白即解析字符串值，紧凑 JSON 手动测试无法暴露。修复后握手 PASS。

验证（本地 `--command` 直跑官方驱动，无需 Docker）：

- `protocol_check` 握手 PASS；**公开 20/20 用例 PASS**（含重启、模式切换、Unicode）。
- `spec_suite.py` 双模式：裸 SQL 229/229；`--jsonl` 241/241（新增大整数 id 回传
  2^53+1、字符串 id、代理对转义、字符串内分号、带空白请求、畸形请求、未知 op、
  shutdown 后退出码 0 且 stdout 静默）。
- 其余回归：run_cases 20/20、hostile 0 失败、fuzz 5/5、scenario 0 失败、
  stress（含增量压缩会话内强杀）216 ok/0 失败。bigdata 1M：装载 36.7s、最慢单响应
  0.309s、RssAnon 80MiB；3M/1.66GiB：装载 181.9s、最慢单响应 0.892s、全表扫描
  10.0s、全排序 14.5s、批量 UPDATE 5.1s、重启恢复 8.1s、RssAnon 245MiB，均 0 失败。
- 官方形状 benchmark（3 轮中位）：T_query 467.7ms、T_write 1659.0ms、
  I/O 5,971,968B 不变、Recall@10=1.0、重启持久 true。复测一轮中位 461.4/1806.3ms；
  协议改造只增加常数级信封拼接，查询仍走原流式路径，与 v10 时点 393ms 的差异
  在本机不同时段波动范围内（六轮 445–557ms），无结构性回退。
